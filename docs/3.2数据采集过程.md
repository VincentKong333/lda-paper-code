# 3.2 数据采集过程

## 3.2.1 技术选型与页面渲染方案

人民网领导留言板（广州市板块）为典型的前端 SPA（单页应用），页面内容由 JavaScript 异步加载，若仅使用 `requests` 抓取静态 HTML 无法获得任何留言数据。进一步分析发现，站点并非服务端渲染，而是通过 XHR 接口以 JSON 形式下发数据，关键接口为：

- 列表接口：`POST /v1/threads/list/df`
- 详情接口：`POST /v1/threads/content`

因此本研究的采集方案**不依赖 Selenium 或无头浏览器渲染**，而是直接逆向上述 JSON 接口、以 Python 原生 `urllib` 构造并发送请求。该方案相较浏览器渲染更轻量、更稳定、资源占用更低，且避免了渲染等待与元素定位带来的不确定性。

接口请求需携带签名。经逆向，签名算法为：

```
signature = md5(接口路径 + JSON(param) + secret + token)
```

其中固定密钥 `secret` 由环境变量 `LIUYAN_SECRET` 提供（不随代码分发），应用标识 `appCode = PC42ce3bfa4980a9`；请求体以 `appCode`、`token`、`signature`、`param`（JSON 字符串）封装后提交。签名校验通过后接口返回标准 JSON，由脚本逐条解析入库。

## 3.2.2 反爬应对策略

平台对高频访问设有请求频率限制（实测当请求间隔低于阈值时返回 HTTP 403）。为在不触发限流的前提下稳定采集，采取以下策略：

- **差异化请求间隔**：列表接口采用约 9 秒（含随机抖动）的间隔；详情接口采用 4.5–6 秒的随机间隔。实测表明 3.5 秒级别间隔即会触发 403 限流，故列表页间隔需显著高于详情页。
- **真实且稳定的请求头**：使用贴近真实桌面浏览器的固定 User-Agent，并完整携带 `Referer`、`Content-Type` 等头字段，以模拟正常浏览器会话、保持会话一致性（频繁更换 User-Agent 反而更易被识别为异常流量）。
- **失败重试与指数退避**：对 403、超时等异常采用指数退避重试，最多 40 次、单次退避上限 600 秒，避免短时密集重试导致 IP 被封禁；退避结束后自动恢复采集。
- **单线程顺序采集**：全程单线程、按 tid 顺序请求，不并发施压，从源头降低被风控的概率。

## 3.2.3 两阶段采集流程

采集中采用「先列表、后详情」的两阶段流程：

- **阶段一 · 列表页 tid 收集**：调用列表接口，按 `fid`（板块编号）分别拉取市委书记（1217）与市长（1218）两个板块。采用游标分页（`lastItem` 字段记录上一页末条），每页 `rows=200`；特别设置 `showUnAnswer=1` 以一并收集「待回复/办理中」等非办结状态留言，避免样本选择性偏差。所有页面的留言唯一标识 `tid` 汇总为待采集队列。
- **阶段二 · 详情页内容提取**：以阶段一得到的 `tid` 逐一调用详情接口，提取留言正文、官方回复正文、回复部门、留言时间与回复时间等字段。
- **断点续跑机制**：脚本记录已采集 `tid`，重启时自动跳过已入库记录，仅补充未完成部分，确保长时任务中断后可无缝恢复、不产生重复数据。

最终共采集市委书记板块 1974 条、市长板块 1374 条，合计 **3348 条**，时间覆盖 2024-08 至 2026-08（受站点「仅开放近两年」限制，最早数据始于 2024-08-21）。

## 3.2.4 数据字段定义

原始数据集每条记录包含以下核心字段（括号内为数据集中的实际列名）：

| 论文字段 | 数据集列名 | 说明 |
|----------|------------|------|
| tid | `tid` | 留言唯一标识 |
| 标题 | `subject` | 留言标题 |
| 正文 | `content` | 留言正文内容 |
| 回复 | `reply_content` | 官方回复正文（待回复样本为空） |
| 回复部门 | `reply_organization` / `reply_dept_level` | 回复机构名称 / 部门层级（本研究统一记为市级） |
| 状态 | `state_info` | 办理状态（已办理 / 办理中 / 待回复） |
| 留言时间 | `create_date` | 留言发布日期 |
| 回复时间 | `reply_date` | 官方回复日期 |
| 板块层级 | `forum_name` / `fid` | 所属板块名称与编号（市委书记 1217 / 市长 1218） |

此外数据集还保留了 `type_name`（留言类型）、`domain_name`（领域）、`nick_name`（网民昵称）、`satisfaction`（满意度）、`reply_delay_days`（派生字段：回复时延，单位天）等共 22 个字段，完整字段表见原始数据文件表头。其中 `reply_delay_days` 由留言时间与回复时间相减得到，直接支撑本研究第 4 章的回复时延分析。

> **⚠️ 与初稿的差异说明（供核对）**
> 你提供的初稿模板为「Selenium 动态渲染 + 3.5–6 秒随机间隔 + 随机 User-Agent + 4 次重试 + 滚动加载」。本节已按**实际采用的方法**如实撰写，主要差异如下：
> 1. **未使用 Selenium**：站点数据走 XHR JSON 接口，直接逆向 API 调用即可，无需浏览器渲染。
> 2. **间隔更长**：实测 3.5 秒会触发 403；列表页用 ~9 秒、详情页用 4.5–6 秒。
> 3. **UA 固定而非随机**：使用稳定真实浏览器 UA + 完整请求头，更稳定且更不易被识别。
> 4. **重试更多**：指数退避最多 40 次（非 4 次），上限 600 秒。
> 5. **列表为游标分页而非滚动加载**：通过 `lastItem` 游标翻页，非前端滚动。
