# 人民网「领导留言板」爬虫 · 交接与部署文档

> **用途**：本研究（广州市留言板数据）采集程序的完整交接文档。
> **目标**：在**另一台电脑**上读完本文档后，无需任何额外沟通即可立刻开始采集。
> **最后更新**：2026-09-14 ｜ 当前已完成采集：广州市委书记(1217) + 广州市市长(1218) 共 **3348 条**

## 一、5 分钟快速上手（TL;DR）

把整个 `liuyan_scraper/` 文件夹拷到新电脑，然后：

```bash
cd liuyan_scraper
python3 check_env.py     # ① 自检（会真实请求接口，约 3 秒）
./start.sh               # ② 一键后台启动采集 + 收尾监控
wc -l collected_1217_1218.jsonl   # ③ 看进度
./stop.sh                # ④ 需要时停止
```

就这四步。**不需要安装任何第三方库**（`pip install` 一次都不用），因为全部代码只用 Python 标准库。

> ⚠️ **唯一必须先读的一点**：目录里已包含之前采集到的 `collected_1217_1218.jsonl`（3348 条）和列表缓存 `list_1217.json` / `list_1218.json`。程序**断点续跑**，会跳过已采的 tid。
> - 如果你**只想采新的板块**（如 11 个区）→ 改 `config.py` 里的 `FIDS`，直接跑即可。
> - 如果你**想把同样的板块重采一遍** → 必须先删除或改名 `collected_1217_1218.jsonl`、`list_1217.json`、`list_1218.json`，否则程序会认为已采完而不做任何事（详见 §7.3）。

## 二、方案总览（原理）

### 2.1 为什么不用 Selenium

站点是前端 SPA（单页应用），页面由 JavaScript 渲染，静态 HTML 里**没有**留言数据。但进一步分析发现：数据并非服务端渲染，而是通过 **XHR 接口以 JSON 形式下发**。因此本方案**直接调用这些 JSON 接口**，不需要 Selenium / Playwright / 无头浏览器。

优点：

| 对比项 | 浏览器渲染方案 | 本方案（直连 API） |
|---|---|---|
| 依赖 | 需 Selenium + 驱动/浏览器 | **零依赖**，仅 Python 标准库 |
| 资源占用 | 高（每个页面渲染） | 极低（纯 HTTP 请求） |
| 稳定性 | 易受页面改版、元素定位影响 | 只要接口不变就稳定 |
| 速度 | 慢（等待渲染） | 快（受限于反爬间隔，非渲染） |

> 目录里保留的 `scraper.py`、`click_more.py`、`probe_pages.py` 是早期用 Playwright 探索时的**废弃脚本**（依赖 playwright，已不再使用），可忽略或删除。

### 2.2 接口与签名（核心）

两个接口：

| 用途 | 方法 | 路径 |
|---|---|---|
| 列表（拿 tid 与元数据） | POST | `/v1/threads/list/df` |
| 详情（拿正文与回复） | POST | `/v1/threads/content` |

请求体结构：

```json
{
  "appCode": "PC42ce3bfa4980a9",
  "token": "",
  "signature": "<签名>",
  "param": "<业务参数的 JSON 字符串>"
}
```

**签名算法**（逆向所得）：

```
signature = md5( 接口路径 + JSON(param) + SECRET + token )
```

- `SECRET`：由环境变量 `LIUYAN_SECRET` 提供，`config.py` 只读取不写入（仓库不含该值）
- `APPCODE = "PC42ce3bfa4980a9"`
- `JSON(param)` 必须用**紧凑格式**（`separators=(',',':')`）且 `ensure_ascii=False`——这是能否通过校验的关键细节。
- `token` 为空字符串（本站未登录也可访问公开留言）。

关键业务参数：

| 参数 | 值 | 说明 |
|---|---|---|
| `fid` | 板块编号 | 1217=市委书记，1218=市长，2813~2824=各区 |
| `showUnAnswer` | **1** | 必须为 1！为 0 会**漏掉所有"待回复/办理中"留言**（曾因此少采 400+ 条） |
| `lastItem` | 上页末条 tid | 游标分页，空字符串=第一页 |
| `rows` | 200 | 每页条数 |
| `orderType` | 2 | 排序方式 |

### 2.3 两阶段采集流程

```
阶段一：列表页收集 tid
  对每个板块 fid，用 lastItem 游标翻页，每页 200 条
  → 结果落盘 list_<fid>.json（缓存，重跑时跳过）
  → 得到该板块全部留言的 tid 清单

阶段二：详情页提取内容
  遍历 tid 清单，逐个调用详情接口
  → 解析 contentList：dataType==1 是留言主体，dataType==4 是官方回复
  → 组装成一条记录，追加写入 collected_1217_1218.jsonl（每行一条 JSON）
  → 每写一条立即 flush，保证中断不丢数据
```

**断点续跑**：启动时先读取输出文件里已存在的 tid 集合，采集时逐个跳过。所以**任何时刻中断都可以，重跑自动续，不会重复**。

### 2.4 反爬节奏（实测调优，不要调快）

| 参数 | 值 | 说明 |
|---|---|---|
| 列表页间隔 | **9 秒**（±1s 抖动） | 实测 3.5 秒即触发 403 |
| 详情页间隔 | **4.5~6 秒**（每次随机） | 原计划 4~6 秒，实测可行 |
| 额外冷却 | 每 40 条详情后冷却 30 秒 | 防止长时高频 |
| 403 退避 | 30→60→120→240→300→420→600 秒 | 指数退避，封顶 600s |
| 最大重试 | 40 次 | 累计退避数小时，足以熬过临时封禁 |

**性能预期**：详情平均约 5.5 秒/条，即约 **650 条/小时**。参考：1217(1974条)+1218(1374条)=3348 条 × 5.5s ≈ **5.1 小时**。13 个板块全量会显著更长，需按天规划。

## 四、换机部署步骤（详细版）

### 步骤 1：拷贝文件

把整个 `liuyan_scraper/` 目录拷到新电脑任意位置（U 盘 / 网盘 / scp / AirDrop 均可）。

**建议只拷必要文件**（省去大文件与废弃脚本）：

```
config.py  scraper_collect.py  analyze.py  monitor_complete.py
check_env.py  start.sh  stop.sh  count_all.py
```
放到新电脑上同一个文件夹即可，例如 `~/liuyan_scraper/`。

> 如果要**接着原有进度**继续采：还需一并拷 `collected_1217_1218.jsonl` + `list_*.json`。
> 如果要**从头采集**：则**不要**拷这三个文件。

### 步骤 2：安装 Python（只需 3.7+，无需任何库）

```bash
python3 -V          # 检查是否已装；macOS/Linux 通常自带
```

没有的话：

- macOS：`brew install python3` 或去 python.org 下载安装包
- Windows：python.org 下载安装，安装时勾选 *Add Python to PATH*

### 步骤 3：环境自检

```bash
cd liuyan_scraper
python3 check_env.py
```

自检会依次检查 Python 版本、依赖、配置、脚本加载，并**真实请求一次接口**验证签名是否有效。出现 `自检全部通过 ✅` 即可开跑。

若报错，看 §10 故障排查。

### 步骤 4：启动采集

```bash
./start.sh
```

`start.sh` 会自动：找 python3 → 检查是否已有进程在跑（防重复）→ 跑自检 → 后台启动采集 → 后台启动收尾监控。

不想跑自检：`SKIP_CHECK=1 ./start.sh`
只想采集、不要自动收尾：`./start.sh --no-monitor`

### 步骤 5：查看进度

```bash
wc -l collected_1217_1218.jsonl    # 已采集条数
tail -f collect.log                # 实时日志
```

## 六、运行与运维

### 6.1 启停

```bash
./start.sh            # 启动（采集 + 收尾监控）
./stop.sh             # 停止（不删数据）
./stop.sh --keep-monitor   # 只停采集，让监控继续出报告
```

也可以手动：

```bash
nohup python3 scraper_collect.py > collect.log 2>&1 &     # 启动
pgrep -f "scraper_collect\.py$"                            # 查进程
kill <PID>                                                 # 停止
```

### 6.2 断点续跑

程序启动时读取输出文件中已有的 tid 并跳过。因此：

- 中断（关机、Ctrl+C、进程被杀）→ 直接重新 `./start.sh` 即可续采
- 不会产生重复记录
- 列表缓存 `list_<fid>.json` 存在时，连列表阶段也跳过，直接进详情

### 6.3 重采同一板块（重要）

若想**把已采过的板块重新采一遍**，必须先清除断点状态：

```bash
# 备份后删除（示例）
mv collected_1217_1218.jsonl collected_old_$(date +%Y%m%d).jsonl
rm -f list_1217.json list_1218.json
```

否则程序会判定"已全部采集"，打印 `本次新增 0 条` 后立即退出。

### 6.4 长时运行（数千条需数小时）

**macOS 防休眠**（重要！合盖/休眠会中断）：

```bash
caffeinate -i ./start.sh
```

**Linux 后台常驻**：

```bash
nohup python3 scraper_collect.py > collect.log 2>&1 &
```

**macOS launchd 守护**（崩溃自动重启，适合跑通宵）：
新建 `~/Library/LaunchAgents/com.you.liuyan.plist`，把路径替换为你的实际路径：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>Label</key><string>com.you.liuyan</string>
    <key>ProgramArguments</key>
    <array>
        <string>/usr/bin/python3</string>
        <string>/Users/你的用户名/liuyan_scraper/scraper_collect.py</string>
    </array>
    <key>WorkingDirectory</key><string>/Users/你的用户名/liuyan_scraper</string>
    <key>KeepAlive</key><dict><key>SuccessfulExit</key><false/></dict>
    <key>ThrottleInterval</key><integer>15</integer>
    <key>StandardOutPath</key><string>/Users/你的用户名/liuyan_scraper/collect.log</string>
    <key>StandardErrorPath</key><string>/Users/你的用户名/liuyan_scraper/collect.log</string>
</dict>
</plist>
```

```bash
launchctl load ~/Library/LaunchAgents/com.you.liuyan.plist     # 加载并启动
launchctl list | grep liuyan                                   # 查看
launchctl unload ~/Library/LaunchAgents/com.you.liuyan.plist   # 停止
```

> ⚠️ **务必只保留一个采集进程**。若 launchd 已在托管，就**不要**再手动 `./start.sh`，否则两个进程同时写同一文件会产生重复数据。用 `pgrep -f "scraper_collect\.py$"` 确认只有一个 PID。

### 6.5 收尾监控（自动出报告）

`monitor_complete.py` 会轮询等待采集结束（目标数达成 / 进程退出且文件稳定 / 停滞 15 分钟 / 超时 12 小时），然后自动：

1. 运行 `analyze.py` → 生成 `采集质量与分布报告.md` + `回复时延分布.csv`
2. 导出原始数据到 `results/`（jsonl 原样 + CSV 表格版）
3. 写 `results/DONE.txt` 完成标记

## 七、数据字段说明

每条记录 22 个字段（`collected_1217_1218.jsonl` 每行一条；CSV 版表头同序）：

| # | 字段 | 说明 |
|---|---|---|
| 1 | `tid` | 留言唯一标识 |
| 2 | `fid` | 板块编号 |
| 3 | `forum_name` | 板块名称 |
| 4 | `subject` | 留言标题 |
| 5 | `type_name` | 留言类型 |
| 6 | `domain_name` | 领域分类 |
| 7 | `state_info` | 办理状态（已办理/办理中/待回复） |
| 8 | `nick_name` | 网民昵称 |
| 9 | `create_dateline` | 留言时间（Unix 时间戳） |
| 10 | `create_date` | 留言时间（`YYYY-MM-DD HH:MM:SS`） |
| 11 | `content` | **留言正文**（LDA 主题建模核心） |
| 12 | `satisfaction` | 满意度（0/1/2 编码） |
| 13 | `from` | 留言来源 |
| 14 | `ip_place` | IP 归属地 |
| 15 | `reply_content` | **官方回复正文**（待回复样本为空） |
| 16 | `reply_organization` | 回复部门 |
| 17 | `reply_dateline` | 回复时间（Unix 时间戳） |
| 18 | `reply_date` | 回复时间（字符串） |
| 19 | `reply_nick_name` | 回复人 |
| 20 | `has_reply` | 是否有回复（1/0，派生） |
| 21 | `reply_delay_days` | **回复时延（天）**，派生 = (回复时间−留言时间)/86400 |
| 22 | `reply_dept_level` | 回复部门层级（1=市级，2=区级，3=街道/镇，派生） |

**论文常用**：LDA 用 `content` + `subject`；时延分析用 `reply_delay_days`；分组用 `fid` / `type_name` / `domain_name`。

## 十、故障排查（FAQ）

### Q1. `check_env.py` 报 HTTP 403

**不是代码问题**，是触发了限流。等待 5~10 分钟再试即可。若频繁出现，把 `config.py` 里的 `LIST_INTERVAL` 调大到 12~15 秒。

### Q2. 报 `ModuleNotFoundError: No module named 'X'`

本项目**零第三方依赖**，出现此错通常是：
- 把 `config.py` 漏拷了（最常见）→ 补上即可
- 或误运行了废弃脚本（`scraper.py` 需要 playwright）→ 改用 `scraper_collect.py`

### Q3. 运行后立刻退出，打印"本次新增 0 条"

断点续跑判定已采完。说明输出文件里已有全部 tid。若要重采，见 §6.3 清除断点状态。

### Q4. 日志一直刷 `[403] ... 退避 600s`

被限流，程序在自动退避等待，**属正常行为，无需干预**。若持续超过 1 小时仍无法恢复，可先 `./stop.sh`，隔几小时再启动（会自动续跑）。

### Q5. 采集很慢

## 十一、注意事项速查

1. **只保留一个采集进程** —— 重复启动会造成双进程重复写数据（`start.sh` 已内置防重，但手动启动时需自己注意）。
2. **别调快间隔** —— 3.5 秒就会 403。
3. **`showUnAnswer` 必须为 1** —— 否则漏掉所有未回复留言。
4. **签名 JSON 必须紧凑** —— `separators=(',',':')` + `ensure_ascii=False`。
5. **重采需先清断点文件** —— 见 §6.3。
6. **长时间跑要防休眠** —— macOS 用 `caffeinate -i`。
7. **macOS 的 `timeout` 命令不存在** —— 如需限时请用 `gtimeout`（`brew install coreutils`）。
8. **数据时间窗受限于近两年** —— 2021~2023 数据无法获取。
